# 反序列化、对象重建与动态解释

涉及序列化库、自定义还原器、持久化对象或跨系统消息。

## 安全属性与成立条件

来自可变边界的数据只能按该接口批准的形状恢复为数据。需要查证当前解析器、配置或业务回调会恢复类型、执行回调或授予对象原本没有的权限。普通 JSON 解析本身只提供数据结构，后续消费决定安全含义。

## 源码调查

查输入来源、真实性校验、实际解析库与版本、时序和输出对象的消费者。阅读 reviver、类型映射、转换 hook、合并操作和动态调用。只验证外层字段时，必须继续检查嵌套数据是如何解释的。

## 控制、对照与反证

用简单数据格式，运行时验证后将允许字段显式构造成业务对象。对不需要的扩展类型和动态执行能力保持禁用。若接口依赖来源认证，核对完整性验证是否发生在解释之前。引用调用者、解析点、对象还原或后续敏感消费。只解析为普通值、白名单映射或数据来源已受可信约束是可验证反证。

## 从数据恢复到能力的边界

定位解析入口的实际模块及版本，区分普通 JSON 值、自定义 reviver、带类型标签的对象重建和解释器执行。标准 `JSON.parse` 在不传 reviver 时读取数据结构。业务层将反序列化字段转成动态构造器、动作选择或路径时，要继续跟踪该消费。验证签名后才恢复允许的结构可以缩小来源范围，但还需看签名密钥是否代表有权指定该类型，以及类型注册表和实例化行为。

例如，消息接收器先验证受信通道，再由 schema 读取纯数据，处理器选择仅由服务端的固定枚举控制，业务服务只接收显式字段。反查队列恢复、重放失败消息和历史导入是否确实共享该契约。若源码显示通用解码器会执行回调、恢复类型或读取外部资源，要说明输入如何到达该分支及可观察效果。仅有 JSON 解析和未使用字段的静态线索，应与之后的查询、原型或对象授权问题分别调查。
